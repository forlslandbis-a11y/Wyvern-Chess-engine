01 — Architecture

Two languages, one game

Python owns training and orchestration. Java owns move search. They're split on purpose — training benefits from PyTorch's ecosystem, search benefits from running close to the metal.

The two talk over a small stateful protocol built for this project, not the standard UCI handshake. Instead of re-sending a full board position on every move, the Java side keeps a live game in memory and just gets told what move was played. Self-play runs thousands of games; that difference adds up.

Chess rules — legal moves, check detection, FEN handling — come from chesslib rather than a hand-rolled implementation.

Python (training) Java (search) ├─ WyvernNet (PyTorch) ◄──► ├─ chesslib rules ├─ self-play workers, ├─ alpha-beta + beam │ one JVM per CPU core │ search, quiescence └─ replay buffer on disk └─ ONNX Runtime eval

02 — Training loop

How it learns

Warm start

Pretraining

Optional supervised pass on real games — Lichess and Chess.com PGNs filtered to 2500+ ELO, roughly 21 million games — before self-play begins.

Self-play

Parallel games

One worker process per CPU core, each with its own JVM, playing games and logging every position: board state, move played, final outcome.

Training step

Policy + value

Cross-entropy on policy, MSE on value, with an entropy term so the policy doesn't collapse too early. Updated weights feed the next round.

Export

Quantize

Weights convert to ONNX, then int8 for faster inference — CPU via AVX2/VNNI, or CUDA where available.

03 — Status

Where it stands

Running on a 4-core Kaggle notebook, and that's the real ceiling right now — self-play throughput scales with CPU core count almost linearly. Over-provisioning workers past the core count was tried once, on the assumption that idle time waiting on search would hide the extra concurrency. Instead the JVMs fought each other for startup time and everything got slower. So the bottleneck is measured, not assumed — more cores would translate directly into more training games per hour.
